LLM foundations — from tokens to alignment

发表于2025-08-24|更新于2026-10-11|English Notes
|浏览量:

Studied summer 2025 · notes tidied up later · 35 min read

中文版：大模型基础：从 Token 到对齐

Worked through the DeepLearning.AI large-model material in late summer 2025, following the Chinese-subtitled Bilibili course. The goal was not to collect prompting tricks. I wanted the whole system: how text becomes numbers, how context gets exchanged, how the next token is chosen, and how a base model becomes something useful.

One small objective, one very large system

An autoregressive language model does one thing: estimate the probability of the next token. Everything else — data, architecture, compute, fine-tuning, evaluation — exists to make that one estimate good.

flowchart TD
  A[Raw text] --> B[Tokeniser splits into sub-words]
  B --> C[Embedding lookup gives a vector per token]
  C --> D[Add positional information]
  D --> E[Stack of Transformer blocks]
  E --> F[Final linear layer gives a logit per vocabulary item]
  F --> G[Softmax makes a probability distribution]
  G --> H[Decoding strategy picks the next token]
  H --> B

I drew this diagram twice before I was happy with it, because the first version left off the arrow that loops back. Generation is not one forward pass. The token the model just produced is appended to the input and the whole path runs again. A hundred-token answer is this loop run a hundred times.

Once that lands, a lot of behaviour explains itself: why generation is so much slower than understanding, because every token traverses the entire network; why the KV cache is such a rescue, because the keys and values of earlier tokens are identical each round and need not be recomputed; why long context is expensive, because the cache grows linearly with length while attention grows with its square.

The other point that gets skipped: the model never chooses anything. It emits a probability distribution over the whole vocabulary, and the choosing happens in the decoding step afterwards. Temperature, top-p and beam search all live outside the model. Separating the two makes tuning far less mystical — if the output is unstable, look at decoding; only if it is wrong should you look at the model.

Finally, nothing in this loop stores memory. The context window is the entire memory, and it is re-read from scratch every round. A multi-turn conversation is just the earlier text pasted back into the input.

Part I — How text becomes computation

1. Tokens are not words

Tokenisation sits between text and the model, and it explains a surprising amount of odd behaviour.

Sub-word schemes such as BPE keep the vocabulary finite while still representing any string. BPE starts from single characters and repeatedly merges the most frequent adjacent pair, so common words end up as one token and rare ones stay in pieces.

Three consequences worth remembering:

  • Arithmetic is hard partly because of tokenisation. If 1234 and 1235 decompose differently, the model does not see a tidy number line.
  • Chinese costs more tokens per character than English does per word, so the same context window holds less Chinese text — and the same API call costs more.
  • Counting letters is hard for the same reason. The model never sees individual characters of a word that arrived as one token.

2. Embeddings and the geometry of meaning

An embedding is a lookup table: token id → a learned vector. Similar meanings end up near each other, and that geometry is learned from co-occurrence alone — nobody defines it.

The same mechanism is what makes vector search work later on in RAG: embed a question, embed the documents, compare directions.

3. Position: attention has to be told

Attention is permutation-invariant by itself — it has no idea which token came first. The cat sat on the mat and the mat sat on the cat would be identical to it. Position has to be added explicitly.

Method How Trade-off
Learned absolute A trained vector per position Cannot exceed the trained length
Sinusoidal Fixed waves of different frequencies Extrapolates somewhat
RoPE Rotates the query and key by an angle proportional to position Encodes relative distance, extrapolates best

RoPE is now the common choice, and the reason is worth holding onto: because it rotates queries and keys rather than adding to the embedding, the dot product between two tokens ends up depending on how far apart they are, not where each sits absolutely.

4. Self-attention is the whole idea

Every token creates three vectors: a query (what am I looking for), a key (what do I offer), and a value (what I actually pass on).

flowchart TD
  A[Token embedding] --> B[Query vector]
  A --> C[Key vector]
  A --> D[Value vector]
  B --> E[Dot product of query with every key]
  C --> E
  E --> F[Scale by square root of head dimension]
  F --> G[Softmax gives attention weights]
  G --> H[Weighted sum of value vectors]
  D --> H
  H --> I[New contextual representation]

Why divide by sqrt(d_k)? Because with large dimensions the dot products grow large, softmax saturates, and gradients vanish. The scaling keeps the distribution soft enough to learn from.

The cost is the part that shapes the whole field: attention is O(n²) in sequence length. Doubling the context quadruples the compute. Every long-context trick exists to attack that number.

5. Multi-head attention

One attention operation produces one view of the relationships. Running several in parallel, each with its own projection, lets different heads specialise.

The total computation is roughly the same as one big head, but the model gets several independent relationship patterns instead of one averaged one. Interpretability work has found heads that track syntax, heads that resolve pronouns, and heads that mostly attend to the first token as a no-op.

6. The Transformer block

flowchart TD
  A[Input] --> B[Layer norm]
  B --> C[Multi-head self-attention]
  C --> D[Residual add]
  A --> D
  D --> E[Layer norm]
  E --> F[Feed-forward network]
  F --> G[Residual add]
  D --> G
  G --> H[Output to the next block]

Two details I had glossed over:

  • The feed-forward network holds most of the parameters. It expands to roughly 4× the model dimension and back. Attention moves information between positions; the FFN does the processing at each position. Roughly two-thirds of a model’s weights live here.
  • Residual connections are what make depth possible, exactly as in ResNet. Without them a 96-layer stack would not train.

Modern models moved layer norm before the sublayer rather than after (“pre-norm”), because it makes very deep stacks train without a warmup schedule.

7. Encoder, decoder, or both

Family Attention Sees Good at
Encoder-only (BERT) Bidirectional Whole sequence at once Classification, retrieval, embeddings
Decoder-only (GPT) Causal mask Only the past Generation, and nearly everything now
Encoder–decoder (T5) Both Input fully, output causally Translation, summarisation

Causal masking is the single mechanism that makes a decoder autoregressive: position i may only attend to positions ≤ i. Implemented by setting the masked scores to −∞ before the softmax, so they become exactly zero weight.

Part II — From base model to assistant

8. Pre-training, and the scaling picture

Pre-training is self-supervised: the label is simply the next token in the text, so no human annotation is needed and the whole internet becomes training data.

The finding that reorganised the field is that performance improves predictably with scale — but only if the three ingredients grow together:

Which is why “how many parameters?” turned out to be the wrong question on its own. A well-trained smaller model is often better and cheaper to serve.

9. Three stages from raw model to assistant

flowchart TD
  A[Pre-training on a very large corpus] --> B[Base model predicts plausible continuations]
  B --> C[Supervised fine-tuning on instruction pairs]
  C --> D[Model follows instructions]
  D --> E[Preference optimisation such as RLHF or DPO]
  E --> F[Aligned assistant]
Stage Data What it changes Relative cost
Pre-training Trillions of unlabelled tokens Knowledge and language ability Enormous
Supervised fine-tuning Thousands of instruction–response pairs Behaviour and format Small
Preference optimisation Human rankings of candidate answers Tone, safety, helpfulness Moderate

The base model is not a bad assistant — it is not an assistant at all. It continues text. Ask it a question and a plausible continuation might be another question, because that is what documents full of questions look like. “Assistant” is a behaviour installed afterwards, and that reframing explains most of what alignment is for.

10. Instruction tuning, in a little more detail

The data is pairs: an instruction, and a good response. Only a few thousand are needed, because the model is not learning new knowledge — it is learning a format and a stance.

Two things the course emphasised:

  • Quality beats quantity, sharply. A few thousand carefully written examples outperform hundreds of thousands of scraped ones.
  • Loss is usually computed on the response only. You do not want the model getting better at generating instructions; you want it better at answering them.

This is also where catastrophic forgetting shows up: fine-tune hard on one narrow task and general ability degrades. Mixing in general data keeps it in check.

11. Learning from preferences

Humans are unreliable at scoring an answer out of ten, but quite reliable at saying which of two answers is better. Both RLHF and DPO are built on that observation.

flowchart TD
  A[Prompt] --> B[Model generates two candidate answers]
  B --> C[A human marks which one is better]
  C --> D[Collect many such comparisons]
  D --> E[RLHF: train a reward model then optimise with PPO]
  D --> F[DPO: optimise the preference directly, no reward model]
  E --> G[Aligned model]
  F --> G
RLHF DPO
Extra model needed Yes, a reward model No
Training stability Fiddly, PPO needs care Much simpler
Pipeline stages Three Two

Both need a constraint that keeps the tuned model close to the original, or it drifts into degenerate text that scores well on the reward model and reads like nonsense — reward hacking, and a good demonstration that optimising a proxy is not the same as optimising the goal.

Part III — Using it

12. Decoding: the same model, different personalities

The model outputs a distribution. How you sample from it changes the output more than most people expect.

Strategy How it picks Good for
Greedy Always the top token Extraction, classification
Beam search Keeps k partial sequences Translation, summarisation
Top-k Samples from the k most likely General generation
Top-p (nucleus) Samples from the smallest set with cumulative probability p The common default
Temperature Flattens or sharpens the distribution before sampling Tuning creativity

Temperature below 1 sharpens toward the likeliest token; above 1 flattens and produces more variety and more errors. For anything factual, low temperature plus top-p is the sane starting point.

Top-p is usually preferred over top-k because it adapts: when the model is confident, the nucleus is one or two tokens; when it is genuinely uncertain, the nucleus widens. A fixed k cannot do that.

13. The context window and the KV cache

Generating token 500 does not mean re-reading the first 499 from scratch. Their keys and values are cached.

That is why long contexts are expensive at inference time and not only at training time, and why context length is a pricing dimension rather than just a feature.

14. Prompting that actually changes behaviour

Most prompt “tricks” are noise. Three are mechanistically real:

  • Few-shot examples. Showing two or three worked examples sets the format far more reliably than describing it. The model is pattern-completing.
  • Chain of thought. Asking for reasoning steps genuinely helps on multi-step problems, because each generated token is extra computation the model can condition on. It is not simulating thought so much as giving itself more working space.
  • Structure the request. Clear delimiters between instruction, context and data reduce the chance that data gets read as an instruction.

What does not reliably help: politeness, threats, claiming urgency, or telling the model it is an expert.

15. Fine-tuning without retraining everything

Full fine-tuning updates every weight and needs optimiser state for all of them. LoRA freezes the base weights and learns a low-rank update instead.

The assumption underneath is that the change needed to adapt a model to a task is low-rank, even though the model itself is not. Empirically that holds well.

Because the base model is untouched, several LoRA adapters can share one set of weights and be swapped at inference. That is why adapter marketplaces exist at all. QLoRA goes further by quantising the frozen base to 4-bit, which is what makes fine-tuning a large model on a single GPU possible.

16. RAG, and why it is not fine-tuning

flowchart TD
  A[User question] --> B[Embed the question]
  B --> C[Search a vector database]
  C --> D[Retrieve the most relevant chunks]
  D --> E[Insert them into the prompt as context]
  A --> E
  E --> F[Model answers grounded in the retrieved text]

Fine-tuning changes behaviour; retrieval supplies facts. If the model writes in the wrong style, fine-tune. If it does not know your documents, retrieve. Choosing the wrong one is an expensive mistake.

The part that is harder than it looks is chunking. Split too small and a chunk loses the context that made it meaningful; split too large and the embedding averages several topics into one vector that matches nothing well. Overlapping windows are the usual compromise.

17. Evaluation, which is genuinely hard

There is no single number. For generation there is often no one right answer, so the usual metrics all measure something slightly beside the point.

Method Measures Weakness
Perplexity How surprised the model is by held-out text Not correlated with usefulness
Benchmarks (MMLU etc.) Multiple-choice knowledge Contamination; not how anyone uses it
LLM-as-judge Another model scores the output Inherits the judge’s biases, prefers longer answers
Human preference What people actually prefer Slow, expensive, subjective

For anything I build myself, the honest approach is a small fixed set of real examples with known good answers, re-run after every change. Unglamorous, but it catches regressions that a benchmark number hides.

18. Hallucination, stated honestly

The objective is next-token plausibility, not truth. A fluent wrong answer and a fluent right answer can score almost identically under that objective. Nothing in pre-training rewards saying “I don’t know” — documents that confidently state things are far more common than documents expressing uncertainty.

Mitigations help without solving it: retrieval grounds answers in real text, low temperature reduces invention, citation requirements make claims checkable, and asking for reasoning steps exposes where an argument breaks. Treating fluency as evidence of correctness remains the most common mistake I see — including in my own early use.

Where this connects

Reading the Mamba component of MM-UNet a few months later was much easier with this background: Mamba exists precisely because attention is O(n²), and a 3D medical volume flattened into a sequence is very long indeed. The courses were separate; the bottleneck turned out to be the same one.
